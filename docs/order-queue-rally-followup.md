# Bounded orders and live rally feedback

This pass covers small controls that previously looked accepted but were not executed consistently: unlimited Shift orders, a paid construction plan accepted after its worker queue was already full, stale unit-target rallies, one displayed rally point despite queued links, and resource orders copied into non-worker queues after the first rally link.

## Evidence

- [Blizzard Special Control](https://news.blizzard.com/en-us/article/4552955/game-guide-special-control) says queued commands have a limit and the player receives a message when that limit is reached. It explicitly includes Stop, Attack, Hold Position, Move, Patrol, and Load/Unload among queueable commands.
- [Blizzard Buildings](https://news.blizzard.com/en-us/article/4488317/game-guide-buildings) describes unit-target and resource-target rally behavior, including workers starting resource collection when produced.
- Native client **4.10.0.75689**, Faster 22.4 loops per second, confirms **32 total Marine orders including the active order**. A paused long Move followed by distinct Shift Move commands retained 31 total when 31 were submitted, 32 when 32 were submitted, and 32 when 33 or 100 were submitted. Raw API acknowledgments remained Success even for discarded overflow, so the acknowledgment alone does not establish acceptance. The native capture agent retained the threshold traces in `traces-worker-transport-20261009/unit-queue-total31.jsonl`, `unit-queue-total32.jsonl`, `unit-queue-total33.jsonl`, and `unit-queue-total100.jsonl` under the local native scratch capture directory. This is a historical-client observation, not a claim about every SC2 build.
- [Pinned Core GameStrings](https://raw.githubusercontent.com/Talv/sc2-data/1921f856b0443d4cbd366c472cd7984fa6a224d1/mods/core.sc2mod/enus.sc2data/LocalizedData/GameStrings.txt) provides distinct messages: `e_cmdOrderQueueIsFull=Cannot queue additional orders` and `e_cmdRallyQueueIsFull=Cannot queue additional rally points`.
- Native Command Center rally tests confirm **four total targets**, including the first point. Produced SCVs inherited three orders after three distinct rally targets, four after four, and four after five or six; trials with 31, 32, 33 and 100 retained the same first four. The raw producer protocol field exposed only the first target, so inspecting that field alone would have led to the wrong limit. These captures are in the same `traces-worker-transport-20261009` directory.
- [Pinned Core UnitData](https://raw.githubusercontent.com/Talv/sc2-data/1921f856b0443d4cbd366c472cd7984fa6a224d1/mods/core.sc2mod/base.sc2data/GameData/UnitData.xml) defaults `ClearRallyOnTargetLost` to 1. [Liberty UnitData](https://raw.githubusercontent.com/Talv/sc2-data/1921f856b0443d4cbd366c472cd7984fa6a224d1/mods/liberty.sc2mod/base.sc2data/GameData/UnitData.xml) overrides it to 0 for `MineralFieldDefault`. Native friendly Marine loss removed that rally head and preserved its following ground target. Native lost MineralField retained the resource location; a produced SCV inherited `HarvestGather295` at that **point**, then its following queued Move. It did not inherit Gather at a surviving resource tag or plain Move for that resource link.
- [Pinned native Galaxy declarations](https://raw.githubusercontent.com/Talv/sc2-data/1921f856b0443d4cbd366c472cd7984fa6a224d1/mods/core.sc2mod/base.sc2data/TriggerLibs/natives.galaxy) expose `UnitRallyPointTargetCount`, `UnitRallyPointTargetPoint` and `UnitRallyPointTargetUnit`, establishing target-list structure. A raw protocol observation that exposes one rally target does not by itself establish an internal chain limit of one.

The unit and rally limits are separate observations. The module applies the four-target default to the current production subset's shared rally path. The threshold capture used a Command Center; a distinct current-build or producer-specific difference would require another native comparison rather than assuming the historical client covers every variant.

## Pure API and integration order

`queueAdmission(unit, {append, deferring, limit=UNIT_ORDER_LIMIT, countsActive=true})` returns `{accepted, mode, count, nextCount, reason}` without changing the unit, its resource phase, its combat or any plan. `UNIT_ORDER_LIMIT` is 32. Shift append counts the active order and successors; normal replacement remains available when the queue is full. A non-Shift command during an uninterruptible worker phase reserves one replacement successor. The existing worker transaction may refund abandoned plans only **after** admission succeeds.

`issue()` must preflight before canceling combat, clearing queues or refunding construction. Building placement must also preflight the chosen builder before deducting resources or spawning a planned structure. Rejected placement keeps money, existing plans and worker state intact. Group commands should count accepted intents, show one overflow error for a rejected subset, and produce success feedback only if at least one intent was accepted.

`orderQueueCount()` also counts the active automatic Repair's saved return Move/Hold/Patrol as one implicit successor, matching the native observation even though this controller stores it in `resume` or `resumeHold`. The caller can use it before an interrupt that preserves the existing tail, so adding automatic Repair and its successor cannot bypass the thirty-two-order bound. Resource intent stored on Return Cargo is not separately counted without a corresponding native observation.

`rallyAdmission(building, order, {append, limit=RALLY_ORDER_LIMIT, visible})` returns a copied replacement or appended chain and rejects an overflowing append with the separate rally message. `RALLY_ORDER_LIMIT` is four. It preserves observed target snapshots. The caller commits `rally`/`rallyOrders` only after acceptance. `cleanRally(building, {entities, minerals, visible})` returns a cleanup patch, guarding hidden remote target state. Ordinary known-lost unit targets are pruned while valid following links survive. A known lost mineral becomes `gatherPoint` at its resource position, preserving the native resource flag exception. `rallyEndpoints(building, {visible})` returns fresh endpoint snapshots for the head and all queued links; friendly moving targets use their current positions instead of the original click coordinates. Only the owner's selected buildings should expose rally intentions in world/minimap rendering.

`spawnRallyOrders(unit, building, {visible})` copies the whole accepted rally chain. SCVs retain resource gathering intent and begin in the outbound phase, including Gather-at-point for a lost mineral location. Every mineral/gas/Gather-at-point link becomes a ground Move for combat units, including links after the head. Copies prevent one spawned unit from modifying another unit's observed endpoint metadata. The worker controller owns local resource acquisition and completion at an empty Gather point; the queue helper does not introduce a global resource search.

## Verification boundary

`node tests/order_queues_followup.mjs` passes 43 checks for default and injected queue limits, replacement/worker deferral, implicit Repair successors, non-mutating rejection, distinct rally rejection, observed snapshots, target cleanup, dynamic/queued display and complete spawned-chain conversion. The 49-check remaining-details browser suite also verifies real paid-build rejection before mutation, queue overflow messages, accepted-cohort feedback, selected-owner rally visibility and newly produced unit execution. These checks establish the implementation contract; the historical native observations above define the practical comparison boundary.
